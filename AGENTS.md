# AGENTS.md

Guidance for AI agents (Claude Code, Hermes, or others) working in this repository. `CLAUDE.md` is a symlink to this file—Claude Code reads `CLAUDE.md` natively, other agent tools increasingly read `AGENTS.md` directly (the emerging cross-tool standard), so one file serves both without duplication.

## What this project is

`klaridian` generates [Model Context Protocol](https://modelcontextprotocol.io) servers from an OpenAPI spec, with observability plugins (starting with OpenTelemetry) wired in automatically. Read [PLAN.md](PLAN.md) for the business/strategy context and [ARCHITECTURE.md](ARCHITECTURE.md) for technical design before making non-trivial changes—both are kept up to date as living documents, not one-off planning artifacts.

**This is Ricardo's project** (github.com/klaridian/klaridian, under the `klaridian` GitHub org he owns).

**Architecture pivot (Aug 30, 2026, ARCHITECTURE.md section 16):** klaridian no longer parses OpenAPI or hand-rolls a mapper (sections 9-15, kept as historical reference—don't resurrect it). OpenAPI parsing / tool-data extraction is delegated to [`openapi-mcp-generator`](https://github.com/harsha-iiiv/openapi-mcp-generator)'s `getToolsFromOpenApi()`.

**v1→v2 cutover (Sep 4, 2026, ARCHITECTURE.md section 49):** the intermediate model—where klaridian consumed `openapi-mcp-generator`'s `generateMcpServer()` *code* output and textually patched it (`render/conformance.ts`, `render/security.ts`, `render/branding.ts`, and the patch half of `render/instrument.ts`)—is **removed**. klaridian now emits the MCP server project itself (`src/emit/*`): a stateless `@modelcontextprotocol/server` (SDK v2, protocol 2025-11-25) project built directly from the tool DATA, with conformance and marketplace annotations native and plugin instrumentation a clean wrap at the `registerTool` boundary. No more textual patching of third-party generated code. Rate limiting, output sanitization, cosmetic icon/website branding, and multi-plugin composition were v1-only and are tracked as follow-ups in section 49.

## Working agreements

- **ARCHITECTURE.md is the source of truth for design decisions and their rationale.** When you make an architectural choice, a real finding, or a scope decision, add it as a new numbered section at the end of ARCHITECTURE.md (don't rewrite history—append, the same way the project's own ADR convention works in spirit, even though this repo doesn't use a separate `docs/adr/` yet). Include *why*, not just *what*.
- **PLAN.md is for business/strategy decisions** (open-core model, plugin priorities, launch channel, etc.), not technical ones. Keep the two documents separate.
- **PLAN.md/ARCHITECTURE.md hold decisions and their rationale; Plane (project MCPFO) holds actionable work and its state.** The split is by axis, not by topic: the "why" of a settled choice is append-only history in the markdown docs, while "what's left to do" and "what state it's in" live as Plane work items. Link the two by reference, never by copying content—a doc section names the ticket (`tracked in Plane: MCPFO-N`) and the ticket cites the section (`PLAN.md §N`). Open a Plane item first when something is just work to do; add a PLAN.md/ARCHITECTURE.md section only once there's a decision with a rationale worth preserving, then close the ticket pointing back at it.
- **Every non-trivial change should be validated end to end, not just unit-tested.** This project's tests intentionally do real `npm install` + `tsc build` + spawn-and-drive-over-stdio-JSON-RPC, because the riskiest failure mode (corrupting the MCP stdio transport) only shows up at that level—see `spikes/001-otel-mechanic/FINDINGS.md` for why. Follow that pattern for new plugins/features rather than only testing generated string content.
- **"Fail loudly, don't guess" still applies to the emitter.** `src/emit/*` and `render/instrument.ts`'s `getPluginProjectAdditions()` throw rather than silently producing a broken or uninstrumented server (e.g. a plugin file-path collision, a code-mode base URL that isn't absolute). Keep that discipline for new emit code.
- **v0 scope is deliberately narrow**—see ARCHITECTURE.md section 8's guardrails (OpenAPI-only input, one plugin per server on the current emitter, no hosted dashboard). Note: the original stdio-only-transport guardrail was lifted in section 29 (`--transport streamable-http` now supported; `web` was removed in the section 49 cutover); the original TypeScript/Node-only guardrail was reversed in section 60 (`--language typescript|python`, full parity, as a forcing function to keep the tool-data IR language-neutral—see section 60 before touching `src/emit/*` or the plugin contract, both of which changed shape there). Don't casually expand scope beyond what's now documented; if a change would cross one of the *remaining* guardrails, flag it explicitly rather than just doing it.
- **Commit and push regularly—don't batch unpushed work.** Commit at the end of each logical unit of work (one ticket, one fix, one finding written up), and push to `origin/main` right after, rather than letting commits pile up locally. `git status`/`git log` should rarely show the local branch more than 1-2 commits ahead of `origin/main`. This repo has no GitHub branch-protection (private repo on the free plan can't enable it—see `gh api repos/.../branches/main/protection`, 403), so CI on `main` is a safety net that only works if pushes happen promptly; a pre-push hook (`.githooks/pre-push`, enabled via `git config core.hooksPath .githooks`) runs the same build+test CI runs, so a broken push fails locally before it ever reaches `origin`.
- **All prose documentation follows the Microsoft Writing Style Guide** (README, this file, PLAN.md, ARCHITECTURE.md, the public docs site, package READMEs — see [STYLE.md](STYLE.md) for the full rule, licensing basis, project-specific exceptions, and how to lint with Vale). This applies to new and edited documentation, not just what existed when the rule was adopted — run `vale <file>` before committing prose changes.
- **`packages/site/content/docs/reference/cli-reference.mdx` is a generated file — never hand-edit it.** It's produced by `packages/cli/scripts/generate-cli-docs.mjs`, which introspects the real `klaridian generate` `commander.js` Command (flag names, descriptions, defaults) — this exists because the hand-written version drifted from the real CLI more than once (documented flags that didn't exist, real flags never documented). After adding/changing any `.option()` in `src/commands/generate.ts`, also update the flag's group in that file's `GENERATE_FLAG_DOC_GROUPS` (the generator fails loudly if a real flag has no group, or a group references a flag that doesn't exist), then run `npm run docs:gen` (packages/cli) and commit the regenerated `.mdx`. CI's `docs-flags-sync` job (and the pre-push hook) run `npm run docs:check` and **fail the build** if the committed file doesn't match what the generator produces from the current code — this is a hard gate, unlike the non-blocking Vale style check.

## Common pitfalls

Real mistakes already made and fixed in this repo—don't repeat them. Each links to the ARCHITECTURE.md section (or file) with the full story; this list only exists so an agent hits the short version first instead of rediscovering it the hard way.

- **Never use `ConsoleSpanExporter`** in generated servers or the `otel` plugin—it writes to stdout and corrupts the MCP stdio JSON-RPC stream. Always `OTLPTraceExporter`, diagnostics to stderr. (`spikes/001-otel-mechanic/FINDINGS.md`)
- **Never run bare `npm install`** for this repo's E2E tests, CI, or devcontainer setup—on some machines it hangs indefinitely on npm's audit/funding network round-trip. Always `--no-audit --no-fund`. (ARCHITECTURE.md section 41)
- **Never treat a timeout-shaped test failure as "raise the timeout" or "reduce concurrency" by default**—reproduce the exact failing command standalone first. The npm-install hang above was first mis-diagnosed as a concurrency problem. (ARCHITECTURE.md section 41)
- **Never trust `npm audit` run against a cloned dependency's own repo** as a real risk signal—re-check from a clean `npm install <package>` as an actual consumer first (its `devDependencies` vulnerabilities don't ship to consumers). (ARCHITECTURE.md section 18)
- **Never assume `openapi-mcp-generator`'s output is stable across versions.** klaridian now depends only on its `getToolsFromOpenApi()` **data** extraction (not its code generator), which is a smaller, more stable surface than the v1 textual patch was—but a version bump can still change tool-data shape (field names, how `baseUrl` is resolved, how parameters are typed). The version is pinned exactly (`openapi-mcp-generator: 4.0.1`, not `^`) for this reason; re-run the real E2E suite after any bump before trusting it. (The old warning here was about `instrument.ts`'s patch being coupled to the `executeApiTool` call site—that patch was removed in the section-49 cutover.)
- **Don't leave empty/dead scaffolding directories after a decision changes**—`packages/runtime-otel/` sat empty and untracked for days after ARCHITECTURE.md section 10 decided against it. Delete the scaffold in the same commit as the decision, not later. (ARCHITECTURE.md section 41)
- **The compiled entrypoint is `dist/src/index.js`, not `dist/index.js`**—`tsconfig.json`'s `rootDir` is `.` (it needs to include both `src/` and `test/`). Double-check `package.json`'s `bin` field stays in sync if this ever changes.
- **The test suite has no fixture-based unit tests for OpenAPI edge cases** (`allOf`/`oneOf`/binary responses/auth/3.1) anymore—those were retired along with the hand-rolled mapper they tested (ARCHITECTURE.md sections 15/17, superseded by section 16). `openapi-mcp-generator` has its own test suite for that; klaridian's tests (`test/*.test.ts`) focus on the emitter output, plugin wiring, and end-to-end CLI behavior instead. Don't try to resurrect the old edge-case tests.
- **Deno must be installed locally (`brew install deno`) for `emit-sandbox-e2e.test.ts` (MCPFO-30) to actually exercise the code-mode sandbox**—those tests skip gracefully (not fail) when `deno` isn't on PATH, so a missing Deno install silently reduces test coverage rather than breaking the pre-push hook. CI installs Deno via `denoland/setup-deno@v2`. If you're working on anything under `src/emit/emit-sandbox.ts`, verify Deno is on PATH before trusting a green local test run.

## Repository layout (see README.md for the full picture)

- `src/emit/`—**the heart of the project since the MCPFO-21 v1→v2 cutover (ARCHITECTURE.md section 49).** klaridian emits the MCP server project itself from the tool DATA: `emit-server.ts` builds a stateless `@modelcontextprotocol/server` (SDK v2, protocol 2025-11-25) project, `emit-tool.ts` emits each `registerTool` call (with native `isError`/`-32602` conformance and marketplace annotations, no textual patching), and `emit-client.ts`/`emit-sandbox.ts`/`emit-docs.ts`/`emit-project-files.ts` cover the code-mode (Deno-sandboxed `execute_code`) architecture and shared project scaffolding. This is where new emit behavior goes; keep the "fail loudly, don't guess" discipline (a plugin file-path collision or a non-absolute code-mode base URL throws rather than emitting a broken server).
- `render/instrument.ts`—collects each plugin's vendored files + npm dependencies (`getPluginProjectAdditions()`) so the emitter can drop them into the generated project, detecting file-path collisions between plugins loudly (`PluginContributionError`). It does **not** patch third-party generated code anymore—the v1 textual patch (`instrumentGeneratedServer()`, coupled to `openapi-mcp-generator`'s `executeApiTool` call site) was removed in the section-49 cutover; instrumentation now wraps natively at the `registerTool` boundary via `plugin.getServerWiring()`.
- `render/license.ts`—generates the `LICENSE` file and `package.json.license` field for the generated project (`--license mit|apache-2.0|none`, default `mit`). See ARCHITECTURE.md section 27.
- `render/auth.ts`—emits the OAuth 2.1 resource-server layer (RFC 9728 PRM, bearer-token/audience validation) for `--oauth-issuer` on streamable-http servers. See ARCHITECTURE.md section 39 / MCPFO-22.
- `packages/cli/src/plugins/`—the `ObservabilityPlugin` interface and individual plugins: `otel/` (engineering observability, any OTLP backend) and three product-analytics plugins—`posthog/`, `amplitude/`, `mixpanel/` (ARCHITECTURE.md section 26 explains why product analytics needed three separate plugins where OTel only needed one: no shared wire protocol on the product-analytics side, unlike OTLP). New plugins implement this interface; see ARCHITECTURE.md section 4 for why it's shaped the way it is.
- `packages/cli/src/commands/` + `src/index.ts`—the actual `klaridian` CLI, built with `commander`. Calls `openapi-mcp-generator`'s `getToolsFromOpenApi()` for pure spec→tool-DATA extraction (a tool-count sanity check and the data the emitter consumes); the MCP server project itself is written by klaridian's own `src/emit/*` emitter, not by `generateMcpServer()` (removed in the section-49 cutover). `render/instrument.ts`'s `getPluginProjectAdditions()` supplies a requested plugin's vendored files + deps to the emitter.
- `examples/petstore/`—the real Swagger Petstore OpenAPI spec, used as the test fixture throughout.
- `spikes/001-otel-mechanic/`—a throwaway, hand-written proof of the OpenAPI → MCP → OTel mechanic, built *before* any generator (hand-rolled or `openapi-mcp-generator`), specifically to catch integration risks early. Keep it as historical reference (see `spikes/001-otel-mechanic/FINDINGS.md`); don't build new features into it. Its core finding (never `ConsoleSpanExporter`, always `OTLPTraceExporter`) still applies and is encoded in `plugins/otel/otel.plugin.ts`.
- `packages/python-posthog-middleware/`—a SEPARATE, independent Python package (ARCHITECTURE.md section 23): a native FastMCP `Middleware` that attaches PostHog product-observability event capture to any FastMCP server (hand-written, `from_openapi()`-generated, or third-party-generated). Deliberately NOT a generator, NOT a patch, NOT sharing runtime code with `packages/cli`—the underlying mechanism is fundamentally different per language (TypeScript emits a whole server project from tool data; Python has a native middleware pipeline to attach to instead). Has its own `pyproject.toml`/`pytest` setup, independent of the Node toolchain. No `otel`-equivalent shipped for Python on purpose—FastMCP already has that natively, so building one would be pure duplication with zero differentiation value.
- `.devcontainer/`—a devcontainer for contributors (PLAN.md section 11), pinned to CI's exact Node 22 / Python 3.11 versions. Validated end to end with the real `@devcontainers/cli` (both packages' test suites run inside it, not just config-parsed).

## Commands

```bash
cd packages/cli
npm install
npm run build            # tsc -p tsconfig.json
npm test                 # builds, then runs real end-to-end tests (npm install/build/run a generated server)

# Manually exercise the CLI:
node dist/src/index.js generate --spec ../../examples/petstore/openapi.json --out /tmp/out --name my-server --base-url https://petstore3.swagger.io/api/v3 [--plugin otel --plugin-config otel.serviceName=my-server]
```
