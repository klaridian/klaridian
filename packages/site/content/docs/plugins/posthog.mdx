## Enabling the plugin

```bash
npx klaridian generate --spec ./api.yaml --plugin posthog
```

Every tool call emits a PostHog event (`tool_name`, `duration_ms`,
`success`) so you can see which tools agents actually use, not just
whether the server is up.

## Why a separate plugin from OTel

Engineering observability (traces) has one shared standard —
OpenTelemetry — so one `otel` plugin covers Datadog, Grafana, Honeycomb,
and any other OTLP backend. Product analytics has no equivalent shared
ingestion standard: PostHog, Amplitude, and Mixpanel each need their own
plugin. `posthog` is the first; `amplitude` and `mixpanel` ship the same
event shape against their own SDKs.

## Configuration

```bash
POSTHOG_API_KEY=phc_... \
POSTHOG_HOST=https://app.posthog.com \
node dist/src/index.js
```

## One plugin per server today

The current emitter supports one plugin per generated server
(`--plugin otel` **or** `--plugin posthog`, not both at once). Composing
an engineering plugin and a product plugin on the same server was
supported by an earlier generation pipeline and is a tracked follow-up,
not yet re-implemented on the current emitter.

## Python / FastMCP

If you're generating for FastMCP directly rather than through klaridian's
TypeScript emitter, see the standalone
[`PostHogMiddleware`](https://github.com/ricardocvasconcelos/klaridian/tree/main/packages/python-posthog-middleware) —
a native FastMCP middleware, not a code generator or patch, for
`mcp.add_middleware(PostHogMiddleware(...))`.
