## The lifecycle

A klaridian project moves through three distinct steps, and it's worth keeping them separate in your head — they run at very different frequencies and have very different constraints.

| Step | Command | How often | Touches the network? |
|---|---|---|---|
| 1. **Decide** | `klaridian generate` | Once per project (or again when a spec/plugin/architecture choice changes) | No, unless you opt in (see below) |
| 2. **Prepare** | `npm install && npm run build` | Once per `generate` (idempotent — nothing to redo until the next `generate`) | Yes — dependency install |
| 3. **Run** | `npm start` or `klaridian start` | Every restart, every deploy | Never |

`klaridian generate` makes every structural decision about a server up front — spec, curation, architecture, plugins, transport, auth. Once that's done, **preparing** (install + build) is a separate, purely mechanical step, and **running** (and restarting) the server is separate again — it never needs generation flags or a rebuild.

```bash
# 1. Decide — generate once
npx klaridian generate --spec ./api.yaml --out ./my-server --base-url https://api.example.com

# 2. Prepare — install and build once
cd my-server && npm install && npm run build

# 3. Run — and re-run on every restart
npm start
```

`npm run build` produces a single self-contained `dist/server.bundle.js` (see [why](/docs/reference/cli-reference#klaridian-generate) klaridian bundles instead of shipping a live `node_modules` tree). `npm start` only runs that file — a restart never re-installs dependencies or touches the network. This is also why `klaridian start` (below) refuses to run `npm install`/`npm run build` on your behalf: step 3 must stay network-free on every single restart, so it can't silently absorb step 2's job without breaking that guarantee.

### `generate --install`: fusing steps 1 and 2

If you don't need to inspect the generated files before installing, `--install` runs step 2 automatically right after `generate` finishes:

```bash
npx klaridian generate --spec ./api.yaml --out ./my-server --base-url https://api.example.com --install
```

This is equivalent to running steps 1 and 2 back to back — it does **not** start the server (that's still step 3, `npm start` or `klaridian start`), and it does **not** change what `generate` decides. `--install` is opt-in and off by default: a bare `generate` stays fast and network-free, which matters in CI, scripting, or when you want to review the generated project before installing anything. The printed "Next" line (and the `--json` output's `nextSteps` field) reflects whichever steps are still left — just `npm start` when `--install` succeeded, the full three-command chain otherwise.

## `klaridian start`

`klaridian start [dir]` is a thin convenience wrapper around the same `npm start` step (step 3 only), for when it's easier to remember one command than "which directory, and which script":

```bash
npx klaridian start ./my-server
```

It takes **no generation flags** — no `--spec`, `--architecture`, `--plugin`, or anything else. Everything those flags would configure is already baked into `./my-server` by the `generate` that produced it. If you want a different architecture, a different plugin, or a different spec, run `klaridian generate` again (optionally into the same `--out` with `--force`) — don't look for a flag on `start`, there isn't one and there won't be.

Two checks run before handing off to the server:

- **Is this a klaridian project?** `start` looks for a `package.json` with a `start` script and a `server.json` (only `generate` emits that). If either is missing, it fails with a clear message instead of a confusing Node error.
- **Has it been built?** `start` checks that the project's `main` entry (`dist/server.bundle.js` by default) exists. If not, it tells you to run `npm install && npm run build` first (or re-run `generate` with `--install`), rather than failing with a generic `MODULE_NOT_FOUND`. `start` deliberately does not run either command for you — see the network note above.

Once those pass, `start` hands stdin/stdout/stderr straight to the generated server (`npm start`, inherited I/O) — this matters for `stdio`-transport servers, where nothing may sit between the MCP client and the server on that stream.

## Configuring a running server

Everything that varies per environment — base URL, auth tokens, plugin credentials, bind host — is read from environment variables by the generated server itself, not passed as a flag to `start` or `generate`. See the relevant how-to page ([OAuth](/docs/how-to/oauth), [plugins](/docs/how-to/plugins), [transports](/docs/how-to/transports)) for which variables apply to your setup.
